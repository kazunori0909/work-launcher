# Phase 29: GitHub Pages のサイト

## 課題

- 使い方の説明はアプリ内のヘルプにしかなく、入れる前の人が読めない
- Web 用に別の文章を書くと、ヘルプと二重管理になる
- Web はトップページやダウンロードなど、ヘルプに無いページも要る。見た目もモダンにしたい

## 方針

- **本文の正はヘルプ**（`src/renderer/src/help/sections/<言語>/`）。Web の docs ページは
  `HELP_BOOKS` をたどって章ごとに作る。章を足す・直すと両方に出る
- **Web にだけ要るページ**（トップ。ダウンロードはトップの1節）は `site/` に置き、ヘルプには入れない。
  文言は `site/src/i18n.ts`（ja が正、en は型で揃える）
- **出し分け**はヘルプの部品 `OnlyApp` / `OnlyWeb`（parts.tsx）で行う（アプリの API を呼ぶボタンなど）。
  どちらで描いているかは `HelpTargetContext`（target.ts）で渡す
- サイトは **Astro** で静的に書き出す。章の本文は React の島として描き、動く見本もそのまま動かす。
  `platform` は Web では Windows / Mac を切り替えられるようにする
- 依存は root の `package.json` に足し、`site/` は node_modules を持たない（React を2つにしない）
- デプロイは GitHub Actions から Pages へ（`https://kazunori0909.github.io/work-launcher/`）。
  出すのは**リリースを公開したとき**と手動のとき。main に入ったまだ配っていない機能の説明を出さないため
- サイトのビルドは CI の check にも入れる（ヘルプの章を直してサイトが壊れたら PR で気づく）
- 章の本文はビルドで HTML に書き出し、ブラウザで hydrate する（検索に載り、見本も動く）。
  DOM が要るもの（html の埋め込みの DOMPurify）は、ビルド時は空で書き出して hydrate 後に描く

## 試作で分かったこと・後回し

- サイトの JS が大きい（共通の塊が約1.2MB、gzip で約330KB）。lucide の全アイコン（アイコン一覧の章）・
  highlight.js・Markdown の描画が入るため。章ごとに分けるのは試作のあと

## 採らなかった案

- ヘルプを MDX にして VitePress / Starlight に載せる … 今の TSX を全部移すことになり、動く見本の扱いも難しい
- Web 用に別の文章を書く … 二重管理になる
- Vite の SPA … HTML が空で検索に載りにくい
