# Phase 9: グループと選択（select）

## 課題

いまの項目は横に並んで折り返すだけで、まとまりは `heading` と `break` でしか表せない。
また、ボタンに渡す値を画面で選ぶ手段が無い。次の3つを足したい。

- **グループ（枠）**: 範囲内のボタンや要素を枠で囲み、ひとまとまりに見せる
- **ボタングループ**: 複数のボタンを1つの塊として並べる。
  例: Excel ファイルなら、ファイル名のボタンの右に「読み取り専用」「フォルダを開く」などの
  小さなボタンがくっついて並ぶ

```
┌ 資料 ─────────────────────────────────┐
│ [ 📊 見積書.xlsx | 読取専用 | 📁 ]    │
│ [ 📊 工程表.xlsx | 読取専用 | 📁 ]    │
└───────────────────────────────────────┘
```

- **選択（select）**: 画面に選択肢（`<select>`）を置き、選んだ値をほかのボタン（実行系・function など）から参照する
  - 選んだ値を記憶するかどうかを項目ごとに選べる。記憶するときは、案件を開き直しても前の選択が有効になる
  - 例: 接続先（dev / stg / prod）を選んでから「デプロイ」ボタンを押す

## 方針

- 3つとも項目（items の1要素）として足す。グループ・ボタングループは子の項目を持つ（入れ子）
  - 開始・終了の印で挟む書き方は、閉じ忘れが起きやすく、YAML の字下げで範囲が見えないため採らない
- 画面からメインへは、項目を「ページ ID ＋ 位置の並び（`[2, 0]` など）」で渡す（入れ子に対応するため）
- select の値は画面が持ち、実行・開く依頼と一緒にメインへ渡す。メインは選択肢にある値だけを受け付ける
  （画面から任意の文字列を入れられないようにする）

## 決定事項ログ

### 2026-11-14: ボタングループの見た目

- ファイル名のボタンの横に操作ボタンがくっついて並び、1つの塊に見える形にする
  （押すとメニューが出る形・同系統のボタンをただ連結する形ではなく）

### 2026-11-14: select を足す

- 選択肢（`<select>`）を項目として置けるようにし、選んだ値をほかのボタン（実行系・function など）から参照できるようにする
- 選んだ値を記憶するかどうかを項目ごとに選べるようにする。記憶するときは、開き直したときに前の選択を有効にする

### 2026-11-14: 書き方と動き（ユーザー承認）

- グループ: `group: 見出し` ＋ `items`。見出しは省略できる（`group:` だけ）。グループの中にグループは置けない
  （入れ子が深くなると枠が重なって見づらいため。要るようになったら外す）
- ボタングループ: `buttons:` に項目を並べる。中に置けるのはボタンになる項目（function・ファイルを開く・実行系・url）だけ
  - `excel` に付けるボタンを指定する省略形は、まず用意しない（書き方が2通りになるため。使ってみて要れば足す）
- select: `select: ID`・`label`・`options`（値だけか `{ label, value }`）・`default`・`remember`
  - 参照は `${select:ID}`（実行系の本文・`env` の値・`url`・`params` の値・ファイルを開くパス・`confirm`）と `ctx.select.ID`
  - `cwd`・`md`・`style` では置き換えない（読み込み時に決まるもので、選択とは時機が合わないため）
  - 同じ ID の select が複数あれば、同じ値を共有する（ページをまたいで同じ選択を出せる）
  - ID の select が無い `${select:ID}` は空文字にし、実行系なら警告を出す（`${env:NAME}` と同じ）
  - 既定値は `default`、無ければ最初の選択肢。記憶した値が選択肢から消えていれば既定値に戻す
- ~~記憶（`remember: true`）は、画面の localStorage に案件フォルダごとに保存する~~ → 2026-11-15 に改めた（下）
  （アプリのユーザーデータの中にあり、案件リポジトリには書かない。メインとのやりとりが要らない）
- ローカル設定の `id` による置き換えは、グループ・ボタングループの中の項目にも届く。新しい項目はページの最後に足す

### 2026-11-15: 項目の tooltip は自前の吹き出しで出す

- OS の吹き出し（`title`）は出るまで約1秒かかり、待たされる感じが強いため、
  画面で描く吹き出し（`data-tooltip`）にして 0.3 秒で出す（ユーザーが試して承認）
- まずは項目のボタンと select だけ。ヘッダー・開始画面・コンソールなどの `title` はそのまま

### 2026-11-15: ボタングループの見本は「読み取り専用が主、編集が添え」

- ファイルはふだん読み取り専用で開き、編集はときどきなので、主のボタンを `readonly: true`、
  添えるボタンをアイコンだけの「編集モードで開く」にする（ヘルプ・仕様書・サンプルで揃える）

### 2026-11-15: select の記憶はメインがファイルに置く（localStorage をやめる）

- localStorage では、アプリを開き直すと記憶が消えていた（ユーザーの確認で判明。→ KNOWLEDGE.md）
- メインがアプリのユーザーデータの `selections.json` に、案件フォルダ → (ID → 値) で置く
  （最近開いた案件の `recent.json` と同じ置き方）
- 記憶した値は案件の読み込み結果（`ProjectView.remembered`）で画面に渡す（開いた直後から前の値を出せる）
- 書くのは `remember: true` の select で、値が選択肢にあるときだけ（メインで確かめる）

### 2026-11-15: radio・checkbox を足す（ユーザー承認）

- `radio: ID` は select と同じキー（`options`・`default`・`remember`）で、選択肢を横に並べたラジオボタンで出す
  （select に表示の指定を足す案は、種類キーで見た目が分かる方が読みやすいため採らない）
- `checkbox: ID` は1つのオン・オフ。値は `on`・`off`（省略時は `true`・`false`）、`default` は true / false
  （options から複数を選ぶ形は、値を1つの文字にまとめる区切りが決めにくいため、まず用意しない）
- 参照は select と共用の `${select:ID}`・`ctx.select.ID`。ID も select と共通
  （種類ごとに変数を分ける案は、変数の仕組みが増えるため採らない）
- 内部では表示の違う select（`control`）として持つ。checkbox は選択肢 [on, off] の select にする
  （値の決め方・記憶・メインでの検証をそのまま使えるため）

### 2026-11-15: ヘルプの見本の select は見本ごとに値を持つ

- 見本の select がその場だけで値を持ち、ボタンの confirm から値が見えなかったため、見本ごとに値を持たせる
- 見本のボタンを押すと、select の値を置き換えた実行内容を見本の下に出す（実行はしない）
- 見本・仕様書・サンプルの select の ID に `env` は使わない（`${env:NAME}` の予約語に見えるため。`target` にする）
- ヘルプ・仕様書では radio と checkbox を別の見出しで書く

### 2026-11-15: ヘルプのサイドメニューを二階層にする（ユーザー承認）

- 章が増えて一覧が見づらくなったため、分類（見出し・押せない）の下に章を並べる二階層にする
- 分類と章:
  - まず読む: はじめに・設定ファイルの編集・ページの追加
  - 要素を追加する: ボタンを追加・ボタン以外の要素・グループとアイコン
  - 設定: 変数・コンソールの色分け・Info ページ・タイトルと見た目
  - 困ったとき: エラーが出たとき
- グループ・ボタングループ・アイコンは、ボタンやラベルの見せ方なので「グループとアイコン」の1章にまとめる
- select は「ボタン以外の要素」の章に置く（ボタン以外の要素を今後足すときは、この章に見出しを足す）
- 設定に `help` ページがあれば、先頭に分類「この案件」を足し、その下に同名の章を1つ出す
