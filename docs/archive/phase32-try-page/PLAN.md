# Phase 32: 体験ページ

## 課題

- サイトでは見本のボタンを押せるが、アプリの画面（タブ・Info）をまとめて触れる場所がない
- ボタンを押したときに、アプリが実際に何をするか（ブラウザで開く・フォルダを開く・コンソールに出る）が伝わりにくい

## 方針

- サイトに体験ページ（`/try/`）を足す。左にランチャーの画面、右にチャット風の吹き出しを並べる
  - ボタンを押すと、右から「押した」吹き出しが出る（自分の発言のように）
  - 続けて左から、実際に何が起こるかの説明の吹き出しが出る
- ランチャーの画面は Top と Info のタブ。Top には URL（パラメータ付き）・フォルダを開く・各種スクリプトのボタンを置く
- ボタンの描画はアプリの部品（`ItemList`）をそのまま使う。開く URL は `buildUrl` で作り、エンコードされた値を見せる
- Info はアプリの `InfoPage` をそのまま描き、`window.launcher.getInfo()` を仮の値を返すものに差し替える
- スクリプトのボタンは OS で出し分けるので、画面の上で Windows / macOS を切り替えられるようにする
- 文言は ja / en の両方を持つ（`site/src/i18n.ts`）

## 決定事項ログ

### 2026-11-23: 画面は左にランチャー、右にチャット風の説明

- ユーザーの指定。ボタンを押すたびに吹き出しが増える。押した操作は右から、起こることの説明は左から出す
- Top・Info のタブを置き、Info は仮の値を出す

### 2026-11-23: サンプル案件の「資料」グループを置く

- ユーザーの指定。Excel・Word のボタン（読み取り専用）と、横に編集モードで開くアイコンだけのボタンを添えた形
  （examples/sample の sample-page.yaml と同じ）
- 説明は OS で分ける。Windows は読み取り専用か編集か、Mac は Office で開き、readonly は効かないこと
- アイコンだけのボタンは、吹き出しにツールチップの文言を出す。サイトでもツールチップが出るよう `Tooltip` を置く

### 2026-11-23: 押したボタンの YAML を自分の吹き出しに出す

- ユーザーの提案。「押した」だけでは、どう書いたボタンかが分からないため
- 書き方は開閉せずにいつも出す。グループの中のボタンは、押したボタンの分だけを出す。radio を変えたときも出す
- 説明の吹き出しにあった開閉式の「設定の書き方」は、重なるので外した

### 2026-11-23: ボタンを絞り、縦幅を詰める

- ユーザーの指定。URL・フォルダのボタンは見出しを付けずに1行に並べる
- スクリプトは、サンプル案件の「コマンド」グループの1行目（bat・sh・PowerShell・Python）だけにする。
  select・radio を使うビルドなどは外した（体験には複雑なため）。残りの5つ（cwd・入力待ち・失敗など）は細かい確認用なので入れない
- 画面の高さは PC で 440px。スマホでは画面のボタンが全部見える 540px にし、チャットは 380px
- 説明が長くても押した操作から読めるよう、チャットは最後の自分の吹き出しより下へは送らない
- スクリプトの本文は自分の吹き出しの YAML に出るので、説明では繰り返さない

### 2026-11-23: コマンドの説明を短くし、変数の展開と失敗を見せる

- ユーザーの指定。コマンドの説明は「コンソールを開き、指定されたコマンドを Git Bash で実行します」の形にする
  （本文は自分の吹き出しの YAML にあるため）
- 設定の変数を展開して渡すときだけ、置き換えることと、置き換えたあとのコマンドを説明に出す。
  見本は `sh: ls "${workDir}/docs"`（select は体験には複雑なので使わない）
- 「失敗する」を足す。サンプルは sh と bat の両方を書くが、YAML が長くなるので sh だけにした（Windows でも Git Bash で動く）
- コンソールの例の色分けは、サンプル案件の console.yaml と同じ rules をアプリの判定（`classifyLine`）に通して付ける
- アプリの `expandVariables` は node:path を使い、ブラウザでは読めないので、体験ページで小さく置き換える

### 2026-11-23: コンソールもアプリの部品で出す

- ユーザーの提案。実行系のボタンを押すと、ランチャーの画面の下にアプリのコンソールが開く
- `window.launcher.onRunEvent` に仮の実行の知らせ（開始・出力を1行ずつ・終了）を流し、アプリの `useConsole`・`Console` をそのまま使う。
  実行中の印・停止・絞り込み・エラー件数・閉じて開き直すまで、アプリと同じに動く
- 説明の吹き出しにあったコンソールの出力の例は外し、「下のコンソールに出ます」とだけ書く
- コンソールを開いてもボタンが全部見えるよう、高さは PC で 600px、スマホで 760px に戻した

### 2026-11-23: 「長い処理」で確認と停止を見せる

- ユーザーの指定。サンプル案件の「長い処理（停止の確認用）」を、sh だけ・ラベル「長い処理」で置く
- confirm はアプリの部品のまま（ブラウザの確認ダイアログ）。OK のときだけ実行し、出力は実際と同じく1秒ごとに 1〜30 と done
- 停止ボタンを押したことも、チャットに吹き出しで出す

### 2026-11-23: Redmine のチケット起票のボタン

- ユーザーの指定。Redmine の新規チケットの URL に `issue[tracker_id]`・`issue[subject]`・`issue[description]` を付け、
  件名と本文のテンプレートを入れた状態で起票画面を開く。複数行の本文は `|` でそのまま書ける
- Redmine の場所は例のためのドメイン（`redmine.example.com`）にする。開いても何もないので「このブラウザで開いてみる」は出さない
- 英語の件名は `(Bug)` にした（`Bug:` は YAML で末尾のコロンがキーの区切りと読まれるため）
- 「未解決の issue」は外した（チケット起票と同じ「パラメータ付きの URL」で役目が重なるため）。1行目は検索・チケット起票・資料フォルダ・README.md
