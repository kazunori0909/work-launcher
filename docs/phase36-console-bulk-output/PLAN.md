# Phase 36: コンソールの大量の出力

## 課題

長いビルド（UE4 など）のように数万行を出すコマンドで、コンソールが重くなる。

- 子プロセスの出力は、届いたチャンクごとに IPC で画面へ送っている。出力が細かいと1秒に数十〜数百回届く
- 画面は受け取るたびに、全行の配列のコピー（2回）・全行の絞り込みと件数の数え直し・最大 5000 個の `<div>` の比較・末尾への追従（レイアウトの計算）をやり直す
- 上限が 5000 行なので、長いビルドでは序盤のエラーが流れて消える。件数も残っている行の中しか数えない
- `\r` だけで上書きするプログレス表示は、終わるまで1行として溜まり続ける（長さの上限が無い）
- `function` から `wait: true` で呼んだときは、出力をすべて溜めてから返す（上限が無い）

## 方針

- メインで、画面へ送る出力を実行ごとに溜め、50ms ごとにまとめて送る。終了・停止の前には残りを送る。stdout と stderr の順番は崩さない
- コンソールの枠（ボタン・件数・絞り込み）は React のままにし、行を並べる部分だけ React の外で DOM に直接足す
  - 上限を超えたら先頭の要素から消す
  - 絞り込みはコンテナの class と CSS で行を隠す（行を作り直さない）
  - 件数は、足した行・消した行の分だけで足し引きする
- 上限の行数は、実機で測って 3 万行にする（→ 決定事項ログ）
- 改行の来ない出力は、行の途中の `\r` を上書きとして最後の分だけ残し、10 万文字を超えたら区切って出す
- 数万行で足りなければ、仮想スクロールに進む（選択・コピー・ページ内検索を補う機能が要るため、まずは見送る）

## 決定事項ログ

### 2026-11-24: 行は React の外で DOM に直接足す

- 仮想スクロールではなく、DOM に直接足す形をまず試す。足した行の分だけ DOM を触るので、全行の比較もコピーも起きない
- 選択・コピー・ページ内検索・折り返しがそのまま使え、変更も小さい
- 採らなかった案: 仮想スクロール（10万行以上も持てるが、画面外の行が DOM に無く、コピー・検索を別に作る必要がある。行の高さが折り返しで変わるので計測も要る）。state の配列をリングバッファやチャンクに替える案（React で描くままなら必要だが、DOM に直接足せば要らない）

### 2026-11-24: 画面への送信を 50ms ごとにまとめる

- 画面の更新を、出力の量によらず1秒に最大 20 回にする。DOM に足す形でも、1回にまとめて足せるので効く
- `function` の `wait: true` で出力を受け取る分は、まとめずにすぐ渡す

### 2026-11-24: 上限は 3 万行、`content-visibility` は使わない

- Mac で、10 万行を出すサンプル（`examples/sample` の「大量の出力」）を実機で測った（→ KNOWLEDGE.md）
- 2 万・3 万行では画面が止まらず、5 万行では 50〜90ms 止まることがあるので、3 万行にする（旧実装は 5000 行）
- `content-visibility: auto` は付けると逆に止まる時間が長くなったので、使わない
- Windows（UE4 を使う環境）は Mac より遅いことがあるので、向こうでも測ってから決め直す

### 2026-11-24: 末尾への追従は、いまの位置で決める

- scroll の知らせは遅れて届き、その間に行が増えたり上の行が消えたりするので、知らせのときに「末尾にいるか」だけを見ると追従が外れる（旧実装でも大量の出力で外れていた）
- 最後に末尾へ動かした位置より上に戻されていたら、使う人が戻したとみなして追従をやめる。行を足すたびにも同じ判定をする

### 2026-11-24: `wait: true` の出力には上限を付けない

- `function` から待って結果を受け取るのは、出力を読んで処理する短いコマンドが主で、大量の出力は考えにくい
- 上限を付けると結果が途中で切れ、読んで処理するスクリプトが誤るので、いまは付けない。困る例が出たら考える

### 2026-11-24: 上限はいったん 3 万行で進め、Windows でも測る

- Windows の結果を見て、大きく遅ければ決め直す
