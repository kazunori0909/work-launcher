# Phase 36 実機で確かめたこと

## 大量の出力の重さ（Mac、2026-11-24）

`examples/sample` の「大量の出力（10 万行）」を押し、終わるまでの時間と、画面が 50ms を超えて止まった間隔を測った
（requestAnimationFrame の間隔。各 2 回）。

| 実装                           | 時間   | 50ms 超の間隔 |
| ------------------------------ | ------ | ------------- |
| 旧（React で描く・5000 行）    | 3.0 秒 | なし          |
| 新・5000 行                    | 2.4 秒 | なし          |
| 新・2 万行                     | 2.4 秒 | なし          |
| 新・3 万行                     | 2.5 秒 | なし          |
| 新・5 万行                     | 2.7 秒 | 50〜90ms      |
| 新・5 万行・content-visibility | 2.8 秒 | 50〜280ms     |

- 旧実装も止まらないのは、5000 行しか持たないため。そのかわり序盤の行は消える
- `content-visibility: auto` は、行が多いほど止まる時間が長くなった（行を足すたびに末尾へ動かすので、
  見える行が入れ替わり続けるためと思われる）

## 大量の出力の重さ（Windows、2026-11-25）

Intel Core i7-10750H・Windows 11。最初の実装（3 万行・ブロックなし・位置で追従）で、Mac と同じ手順を流した。

- bat で 10 万行は約 9.4 秒。遅さの大半は cmd.exe の `for /l` と `echo` で、出力を nul に捨てても 7.6 秒かかる。表示側がボトルネックではない
- 50〜87ms の止まりが 18〜22 回。古い行を 3000 行ずつ消す回数（約 23 回）とほぼ同じ
- node で 10 万行を一気に出すと、0.7〜0.85 秒で終わるが、250〜360ms の止まりが 2 回出た
- 停止すると、`taskkill /F` の終了コード 1 で「失敗（コード 1）」と出た。cmd.exe は残らない
- bat の日本語の出力は化けない

## 行をブロックに入れた効果（Mac、2026-11-25）

20ms を超えたフレームの数で比べた。slow は 2000 行ごとに 0.15 秒休みながら 10 万行を出す（Windows の bat に近い出方）。
burst は node で 10 万行を一気に出す。

| 実装                                 | slow（20ms 超）   | burst（50ms 超）   |
| ------------------------------------ | ----------------- | ------------------ |
| コンテナの直下に並べる               | 45 回（20〜39ms） | 102〜123ms が 2 回 |
| 500 行ずつのブロック・1 フレーム 8ms | 3 回（約 21ms）   | 88ms が 1 回       |

- コンテナの直下の行数が多いほど、行を足すたびの止まりが長くなっていた（行の数に比例する再計算）

## 値を変えて測った結果（Mac、2026-11-25）

slow・burst は上と同じ。「出るまで」は、押してから最後の行が画面に出るまで。各 1〜2 回。

ブロックの大きさ（1 フレーム 8ms）:

| ブロック       | slow（20ms 超）   | burst の最大の止まり | burst の出るまで |
| -------------- | ----------------- | -------------------- | ---------------- |
| 1 つにまとめる | 49 回、最大 151ms | 約 950ms             | 1.5〜2.5 秒      |
| 100 行         | 0 回              | 60〜66ms             | 0.27〜0.37 秒    |
| 500 行         | 0 回              | 62〜70ms             | 0.29〜0.32 秒    |
| 2000 行        | 29 回、最大 34ms  | 92〜123ms            | 0.34〜0.44 秒    |

1 回に送る行の上限（ブロック 500 行）: 500 行・2000 行・1 万行・上限なしで、burst の最大の止まりは
62〜93ms、出るまでは 0.27〜0.36 秒。値による差ははっきりしない。

1 フレームの時間（ブロック 500 行・上限なし）: 8ms ずつなら burst の最大の止まりは 85ms、一度に全部足すと 147〜154ms。
出るまではどちらも約 0.28 秒。

- どの値でも、子プロセスが終わるまでの時間は変わらなかった（slow 約 9.7 秒、burst 0.15〜0.28 秒の範囲でばらつく）
- Windows は Mac の約 4 倍遅いので、Mac で 30ms 台の止まりは向こうで 100ms を超えうる

## 末尾への追従が外れる

- scroll イベントは scrollTop を変えた後に遅れて届く。その間に次の出力で行が増えると、
  届いたときには末尾から離れているので、「使う人が上に戻した」と誤る（旧実装でも 10 万行で外れていた）
- 古い行を上から消すと、ブラウザのスクロールアンカーが見ている行を保とうとして、末尾から離れる。
  `.console-body` に `overflow-anchor: none` を付けて止めた
- 位置で判定する形（最後に末尾へ動かした位置より上なら、使う人が戻した）でも、Windows で少しずつ出るときに外れた。
  古い行を消すと位置が末尾に合わせて下がり、その後に行が増えてから scroll の知らせが届くため
