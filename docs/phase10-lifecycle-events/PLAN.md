# Phase 10: イベント（change・起動・終了）

## 課題

- select・radio・checkbox の値が切り替わったときに、案件ごとの処理を動かしたい
- 案件を開いたとき（起動）・閉じるとき（終了）にも、案件ごとの処理を挟みたい
  - 例: 起動時に記憶した接続先に合わせて準備する、終了時に後片付けをする
- 起動時の処理は、select ごとに change を呼ぶのではなく、1か所にまとめて書けるようにしたい

## 方針

- **イベントは決まった名前の関数で受ける**。設定ファイルに関数名を書かせず、`scripts` の JS に
  決まった名前の関数があれば呼ぶ（設定項目を増やさず、「要るなら中身を書き換える」と分かるため）
- **アプリの基底処理の前後に挟む**（ゲーム開発でよくある形）。何か足したいときは、前か後の好きな方に書く
  - `beforeOpen` / `afterOpen` … 起動の基底処理の前後
  - `beforeClose` … 終了の基底処理の前。終わるまで閉じずに待つ
- 空の関数（中身はコメントだけ）を、サンプル案件の `launcher/scripts/` に**サンプルとは別のファイル**で置き、
  ヘルプにも同じ雛形を載せる（いまは案件の雛形を作る機能が無いため）
  - change に書く関数（例 `onTargetChange`）は、サンプルの関数なので `sample-scripts.js` に置く
    （イベント用のファイルには、決まった名前の起動・終了の関数だけを置く）
- **全体の処理（起動・終了）は決まった名前の関数、change は項目ごとの指定**にする
  - change は select・radio・checkbox に `change: 関数名` と書き、その項目が変わったときだけ呼ぶ
- change は、開いたときの値の復元では呼ばない（「人が値を変えた」という意味だけにする）。
  開いたときの処理は `afterOpen` などにまとめて書いてもらう

## 決定事項ログ

### 2026-11-15: イベントは決まった名前の関数で受け、基底処理の前後に挟む（ユーザー提案）

- 設定ファイルに関数名を書く形（`startup: init` など）ではなく、`scripts` に決まった名前の関数を置く
  （設定項目が少なく、空の関数があれば「要るなら書き換える」と分かるため）
- 名前は `onPreStartup`・`onPostStartup`・`onPreCleanup`（→ 下の「関数名を beforeOpen などにする」で改名）。足したい処理は前後の好きな方に書く
- 空の関数はサンプルとは別のファイルで、イベント用として用意する
- change は開いたときの値の復元では呼ばない。開いたときの処理は起動イベントにまとめる

### 2026-11-15: change は select 系の項目ごとの指定にする（ユーザー決定）

- select・radio・checkbox に `change: 関数名` と書き、その項目が変わったときだけ呼ぶ
- 決まった名前の1つの関数ですべての change を受ける形（`onPostChange` など）は採らない。
  どの項目の変更かを関数の中で見分けることになり、条件の書き間違いで別の項目の処理が動くおそれがあるため
- 決まった名前の関数で受けるのは、起動・終了のような案件全体の処理だけにする
- サンプルで change に使う関数は、サンプルと分かるように `sample-scripts.js` に置く

### 2026-11-15: 未決の 1〜7 を決める（ユーザー判断）

- **起動**: 基底処理 = 設定を読んだあと、select の値を決め（記憶の復元・既定値）、案件の画面を出すまで
  - `beforeOpen` は値を決めたあと・画面を出す前に呼び、終わるまで案件の画面を出さない。
    `ctx.select` には決まった値を渡す（前後で同じ値を受け、違いは画面を出す前か後かだけにする）
  - `afterOpen` は画面を出したあとに呼ぶ
  - 設定の読み込みより前には挟めない（`scripts` の場所が設定に書いてあるため）
- **change の ctx**: `ctx.changed = { id, value, previous }` と、いつもの `ctx.select`（変えたあとの値）
- **実行の許可**: `scripts` がある案件で、まだ許可していなければ、開いた直後に確認する。
  許可されなければイベントは呼ばない
  - 案: 許可済みのときだけ呼び、開いたときは確認しない → 許可するまで起動イベントが動かず、気づきにくいため採らない
- **終了**: 基底処理 = 実行中のプロセスを止める。閉じる・別の案件に切り替える・アプリを終了するとき
  - `beforeClose` が終わるのを待ってから、決まった名前の待ち関数 `canClose` をくり返し呼ぶ。
    `true` を返したら終わったとみて閉じ、`false` なら少しおいてまた呼ぶ。`canClose` が無ければ待たない
    （→ 下の「canClose をやめる」で取り消し）
    （`beforeClose` で止め始め、止まったかは別に確かめる形を書けるようにするため）
  - 待つ間は、待っていることと「待たずに閉じる」ボタンを出す。上限の時間は設けない
    （固まっても人が閉じられ、重い後片付けを時間で切らないため）
  - 案: 上限の時間（5秒など）で打ち切る → 後片付けの重さは案件ごとに違い、決めた時間で切ると途中で止まるため採らない
- **設定の読み直し**（ファイル保存）では起動イベントを呼び直さない
- **change が続けて来たとき**は、前の処理が終わってから順に呼ぶ
- 関数は呼ぶたびに別プロセスで JS を読み直すため、イベントの間でメモリ上の値は持ち越せない。
  要るならファイルに書いてもらう（ヘルプに書く）

### 2026-11-15: 関数名を beforeOpen などにする（ユーザー判断・Claude 提案）

- `onPreStartup`・`onPostStartup`・`onPreCleanup`・`onWaitCleanup` を、
  `beforeOpen`・`afterOpen`・`beforeClose`・`canClose` にする
- 画面・メニューの言葉（案件を開く・閉じる）に合わせる。Startup だとアプリの起動と取り違えやすいため
  （ウィンドウごと・案件の切り替えでも呼ぶ）
- 前後は before / after で表す（Jest・Vue などでよく見る形）。`on` と Pre が重なって長くなるのを避ける
- 待ち関数は true / false を返すので、問いの形の `canClose` にする（→ 下の「canClose をやめる」で取り消し）
- 案: `onBeforeOpen` など `on` を付ける → 長くなるだけで、わかりやすさは変わらないため採らない
- 案: `activate`・`deactivate`（VS Code の拡張と同じ）→ 画面を出す前と後に分けた名前が作りにくいため採らない

### 2026-11-15: 仕様を書くときに決めた細かい点（Claude 提案）

- `beforeOpen` の間は、案件の画面の代わりに「準備中」を出す
- 例外が出たらコンソールにエラーを出し、画面を出す・閉じるは続ける（関数の誤りで開けない・閉じられないのを避ける）。
- 同じ名前のイベント関数が複数のファイルにあれば、呼ばずにエラーを出す（function と同じ）
- 省略時の `launcher/scripts/` が無いときは何も出さない。書いたファイルが無いときはエラーを出す
- 同じ ID の項目が複数あれば、画面で操作した項目の `change` を呼ぶ
- アプリを終了するときは、ウィンドウごとに `beforeClose` を呼び、すべて閉じてから終了する
- 仕様は docs/config.md の末尾に「10. イベント」として足す（4章以降の番号を参照しているところがずれないため）

### 2026-11-15: イベント用の JS は関数をコメントにして置く（ユーザー判断）

- サンプル案件の `launcher/scripts/events.js` に、`beforeOpen`・`afterOpen`・`beforeClose` を
  コメントにして置く。使うものだけコメントを外す
- コメントにしておくと、使っている関数がコメントを外したものだけになり、見分けやすい。
  空の関数を呼んでも動きは変わらないので、どちらでもよい

### 2026-11-15: canClose をやめ、beforeClose を待つ（ユーザー判断）

- 待ち関数 `canClose` は作らない。`beforeClose` が終わるまで（async なら Promise が終わるまで）閉じずに待つ
- 後片付けが終わるのを待つ処理は、`beforeClose` の中で `await` して書ける。くり返し呼ぶと、そのたびに
  別プロセスで JS を読み直すうえ、関数の間で値を持ち越せないため
- 待つ間は「待たずに閉じる」を出し、押されたら関数のプロセスを止めて閉じる。上限の時間は設けない（前の決定のまま）

### 2026-11-15: 実装で決めたこと（Claude 提案）

- 「別の案件に切り替える」はいまのアプリに無い（案件は開始画面か新しいウィンドウで開く）。
  閉じるイベントは、ウィンドウを閉じる・アプリを終了するときだけ呼ぶ
- 画面で select の値を変えるたびにメインへ知らせる（`rememberSelection` を `changeSelection` にまとめる）。
  メインがいまの値を持ち、`beforeClose` などの `ctx.select` に渡すため。記憶と change の呼び出しもここで行う
- change の関数名は画面から受け取り、その ID の項目にその `change` が書いてあるかをメインで確かめる。
  関数はその項目のページの `cwd` で動かす（function の項目と同じ）
- `afterOpen` は、`beforeOpen` のあと案件を画面に返した直後に呼ぶ（画面から「出した」の知らせは受けない）。
  呼ぶまでに別プロセスを立ち上げるため、実際には画面が出たあとに動く
- `beforeOpen` の間は、画面はいまの「読み込み中…」のまま（「準備中」と出し分けない）
- 「待たずに閉じる」は、待ち始めて 0.5 秒たっても終わらないときに画面の上に帯で出す
  （すぐ終わるときにちらつかないため。コンソールの `ctx.log` が見えるように画面全体は覆わない）
- イベントで実行を許可しなかったら、その案件を開いている間は聞き直さない（function のボタンは押すたびに聞く）
