# Phase 1: 全体設計

## 課題

1. 開発案件ごとに、よく使うコマンド・ファイル・URL をまとめて開けるランチャーが欲しい。
   Windows と macOS の両方で動かしたい
2. アプリ本体は OSS としてビルド・配布し、案件側は設定ファイルの追加・編集だけで反映できるようにしたい
3. 設定は、パスの `\\`・複数行コマンド・区切り文字の打ち間違いで壊れにくい書き方にしたい

## 要件

- 案件ごとに、ページ・ボタンを追加できる
- 共通機能としてメイン・マニュアル・Info（PCスペック）ページがある
- 案件の共通設定とは別に、ローカルだけで既存ページへの追加・新規ページの追加ができる
- 項目の種類
  - ボタン（関数呼び出し、`tooltip`・`confirm`・`icon`）
  - ファイルを開く（`excel`・`powerpoint`、`readonly`）
  - 実行（`bat`、複数行。sh・powershell・python にも対応したい）。出力はアプリ内コンソールに出す。
    コンソールの色・パーサー設定は別ファイルで持ちたい
  - 埋め込み（`html`・`markdown`・`mdfile`）
  - URL（`params` は自動で URL エンコード）

## 方針

### 技術: Electron

| 観点                       | Electron  | Tauri                  | Neutralino |
| -------------------------- | --------- | ---------------------- | ---------- |
| 外部 JS を実行時に読み込む | ◎         | △ 権限設定と制約が多い | ○          |
| 任意コマンド・exe の実行   | ◎         | △ 事前の許可リスト制   | ○          |
| 配布サイズ                 | ✕ 約100MB | ◎ 数MB                 | ◎          |
| 情報量・成熟度             | ◎         | ○                      | △          |

- 「設定に書いたコマンドを何でも実行する」用途に最も素直に合うため Electron を推す
- Tauri は実行コマンドを事前に許可リストへ書く設計で、案件ごとに自由に書き換える方針と相性が悪い

### 設定の書き方: 宣言は YAML、処理は JS

- ボタン・ページは YAML。パスはエスケープ不要、複数行コマンドは `|` で bat と同じ感覚で書ける
- 関数は `.launcher/scripts.js` に置き、YAML から名前で呼ぶ
- JSON Schema を配布し、VS Code で補完・エラー表示を効かせる
- 1項目に `bat` と `sh` を両方書けば OS に合う方を実行。片方だけなら他 OS では無効表示
- 変数 `${projectDir}`・`${env:NAME}` をパス・コマンド中で使える

### ファイル構成

```
<案件リポジトリ>/
  work.launcher           ← 案件の設定（コミットする）。ダブルクリックで起動
  work.local.launcher     ← 個人用（.gitignore）
  .launcher/
    scripts.js               ← ボタンから呼ぶ関数
    console.yaml             ← コンソールの色分け・パーサー（正規表現 → 色/レベル）
    pages/*.yaml             ← ページの分割
    help/*.md
```

- ローカル設定はページ ID で合成する。同じ ID なら項目を追加（`replace: true` で置き換え）、
  新しい ID ならページを追加

### Info ページ

- CPU・メモリは常に表示
- ドライブ: ローカル+ネットワーク（Mac はマウント中のボリューム）
- 指定した環境変数
- ツールのバージョン: git・node・python 等は取得方法を組み込みで持つ。
  無いものは `command`（と出力から抜き出す `pattern`）を設定で直接書く

### 既知の制約

- Mac の Excel には Windows の `/r` に当たる読み取り専用オプションが無い。
  AppleScript での対応を試し、駄目なら通常の開き方にする

## 決定事項ログ

### 2026-11-13: 起動・ウィンドウ・書き方の前提

- 対象アプリ（案件のファイル）を起動すると、その案件の設定で開く（ユーザー判断）
- ウィンドウは案件ごとに分ける（扱いやすいため。ユーザー判断）
- Info の表示項目は CPU・メモリ・ネットワーク含むドライブ・指定環境変数・
  指定ツールのバージョンとする。バージョンの取り方はツール定義に内包し、コマンド直接指定も可
- 設定の書き方は、URL 引数や bat 等のコマンドを直接書きやすいことを優先する（ユーザー判断）
- 開発はプチ仕様駆動で進め、`docs/` に記録を貯める。トークン利用を抑える工夫も試行錯誤する

### 2026-11-13: 技術と設定の書き方を確定

- 技術は Electron にする（任意コマンドの実行と外部 JS の読み込みに素直に合うため。ユーザー承認）
- 設定は宣言を YAML、処理を `.launcher/scripts.js` に分ける（ユーザー承認）
- 拡張子 `.launcher` をアプリに関連付け、`work.launcher` のダブルクリックで
  その案件のウィンドウを開く（ユーザー承認）

### 2026-11-13: 開発環境はホスト、devcontainer は使わない

- 開発・起動・ビルドはホスト（macOS）で直接行う。Electron はホスト OS で動かすこと自体が目的で、
  コンテナに入れると画面表示と OS 固有機能（関連付け・bat・Excel・ドライブ情報）の確認が遠くなるため
  （ユーザー承認）
- 環境の揃え方は Node.js のバージョン固定で代える（mise か Volta。ユーザーが既に使っている方を Phase 2 で確認）
- 雛形は electron-vite、配布ビルドは electron-builder（`fileAssociations` で `.launcher` を関連付けられるため）、
  言語は TypeScript
- 設定の読み込み・合成などのロジックは Electron に依存しない形に分ける（テストを速く、CI で回しやすくするため）
- Win / Mac 両方のテスト・ビルドは GitHub Actions（`macos-latest` / `windows-latest`）で回す。
  リポジトリを GitHub に置く段階で入れる。bat・Excel 等の実動作は Windows 実機で最後に確認する

### 2026-11-13: 実行系の作業フォルダを設定で指定できるようにする

- `cwd` を最上位・ページ・項目に書け、項目 → ページ → 最上位の順に引き継ぐ。既定は `${projectDir}`、
  相対パスは `${projectDir}` 起点、絶対パスも可（→ docs/config.md 3.3）。
  案件で作っているスクリプトを、ランチャーから短く呼び出せるようにするため（ユーザー判断）
- 案: 変数（例 `${scriptDir}`）を足す方法もあったが、作業フォルダを決めれば本文にファイル名だけ書けば済み、
  覚えることが増えないため `cwd` の引き継ぎにした

### 2026-11-13: 設定ファイル仕様を確定（→ docs/config.md）

- ページの分割は自動で読まず、`pages` に `include` で並べる（表示順が1か所で分かるため）
- 実行系の値はスクリプト本文とし、一時ファイルに書き出して実行する。パスかどうかで書き分けない
- 変数は `${projectDir}`・`${env:NAME}` の形だけを置き換え、ほかの `${...}` は残す（sh の変数とぶつけないため）
- ローカル合成に項目 `id` による置き換えを加える
- 相対パスは `${projectDir}` 起点（`mdfile` 内のリンクだけはファイル起点）
- 追加: 種類 `open`、実行系の `cwd`・`env`・`encoding`、`.launcher/console.local.yaml`
- `html` の `<script>` は実行しない
- 以上、ユーザー確認済み。scripts.js を初回に信頼確認するかは Phase 2 で決める
