# Phase 2: 最小構成の実装

## 課題

- Phase 1 で決めた仕様（[docs/config.md](../config.md)）が実際に動く形になっていない
- まず「案件の設定を読んで、ボタンからコマンドを実行し、出力を見る」一連の流れを通したい

## 方針

### 範囲

- 入れる: `work.launcher` の読み込みとローカル合成、トップページの表示、
  実行系（`bat`・`sh`）と `function`（scripts.js の関数）、コンソール（`console.yaml` の色分け）、
  `open`（ファイル・フォルダを開く）、`url`（既定のブラウザで開く）
- 入れない（Phase 3 以降）: Info・マニュアル・埋め込み・`excel`/`powerpoint`・JSON Schema・
  `.launcher` の関連付けと配布ビルド

### 構成

- 設定の読み込み・合成・変数置き換えは Electron に依存しないモジュールに分け、単体テストする（CLAUDE.md）

### 着手前に決めること

- Node.js の固定に mise と Volta のどちらを使うか（ユーザーが既に入れている方）、Node.js のバージョン
- パッケージマネージャ
- git リポジトリ化（`git init`）するか
- scripts.js を初めて開く案件で読み込む前に、信頼の確認を出すか

## 決定事項ログ

### 2026-11-13: 開発環境と scripts.js の扱い

- Node.js の固定は mise（`mise.toml`）。Node.js 以外のツールもまとめて固定できるため（ユーザー承認）
- Node.js は LTS の 24 系（奇数バージョンの 25 は長期サポートが無いため。ユーザー承認）
- パッケージマネージャは npm（追加の導入が要らず、GitHub Actions でもそのまま使えるため。ユーザー承認）
- この段階で `git init` する（ユーザー承認。コミットは指示があったときだけ）
- 初めて開く案件では、scripts.js を読み込む前に信頼の確認を出す。
  配られた `work.launcher` のダブルクリックだけで任意コードが動くのを防ぐため（ユーザー承認）
- 画面は React + TypeScript（設定に合わせた描き直しを素直に書け、情報量が多いため。ユーザー判断）

### 2026-11-13: 案件のタイトルと個別 CSS

- 複数のランチャーを並べてもどの案件か分かるように、最上位の `title` をヘッダーに控えめに出す
  （大きい見出しにはしない）。ウィンドウタイトルにも使う（ユーザー判断）
- 案件ごとの見た目は最上位の `style`（CSS ファイルのパス）で変えられる。work.launcher と
  work.local.launcher の両方に書け、ローカルを後に当てる（ユーザー判断）
- 既存の `name` は `title` に改めた（ページの `title` と揃えるため。公開前なので互換は持たない）
- 色だけ変えたい案件が多いと見て、ヘッダー・強調色などは CSS 変数で上書きできるようにし、その一覧を
  docs/config.md に書く（クラス名に頼る書き方より壊れにくい）

### 2026-11-13: 実行時の入力待ちは止まらずに進める

- 実行系の標準入力は空にし、bat の `pause`・`set /p` などの入力待ちで止まらず進むようにする。
  ランチャーのコンソールは出力を見る場所で、入力は受けないため（ユーザー判断）
- 案: コンソールから入力を送る方法もあったが、最小構成では入れない

### 2026-11-13: コンソールは要るときだけ開く

- コンソールは最初は閉じておき、実行系（bat・sh 等）を始めたときと、操作のエラーが出たときにだけ開く。
  ファイル・URL を開く、function を押すといった操作では開かない（ユーザー判断）
- 閉じても内容は残し、タブの並びの右端のボタンから開き直せる

### 2026-11-13: 実行の始めに作業フォルダをプロンプトの形で出す

- コンソールで、実行の始めに作業フォルダを `C:\work>`（bat）・`PS C:\work>`（powershell）・
  `/work $`（sh・python）の形で出す。ターミナルと同じ感覚でどこで動いたか分かるようにするため（ユーザー判断）
- 出すのは実行を始めた時点の場所だけ。スクリプト内の `cd` までは追わない
- 開始はメインから知らせる（作業フォルダを知っているのはメインで、警告・出力・終了と順序も揃うため）

### 2026-11-13: open と url を Phase 2 に入れる

- フォルダを開く（`open`）と、既定のブラウザで開く（`url`）を Phase 2 に足す（ユーザー判断）
- 失敗したとき（パスが無い・URL が不正など）だけコンソールにエラーを出す。成功時はコンソールを開かない

### 2026-11-13: function（scripts.js）の動かし方

- 押すたびに `utilityProcess` で別プロセスを起こして関数を呼ぶ。scripts.js の誤りや無限ループで
  アプリ本体が固まらず、編集がすぐ反映されるため。案: メインで `require` する方法は速いが、上の2点を失う
- 信頼の確認は案件フォルダ単位。初めて function の項目を押したとき（scripts.js を読み込む前）に出し、
  信頼した案件はアプリの設定フォルダ（userData）に記録する。案: 内容のハッシュで聞き直す方法は、
  開発中に編集のたびに聞かれて煩わしいため採らない
- `ctx` は `projectDir`・`env`・`log(text)`・`open(path)`・`openUrl(url, params)`。ほかは Node の機能を直接使う
- `log` はコンソールに書くが開かない。例外のときだけ開く（ボタンでコンソールは要らない、の方針に合わせる）

### 2026-11-13: scripts.js の関数を呼ぶ種類キーを `function` にする

- `button` を `function` に改めた。画面上はどの項目もボタンで、`button` では何が起きるか伝わらないため。
  ほかの種類キー（`bat`・`open`・`url`）と同じく、動作が分かる名前にそろえる（ユーザー判断）
- 案: `call`（短いが何を呼ぶか分かりにくい）、`js`（bat 等は値が本文なのに対し、こちらは関数名で混同しやすい）

### 2026-11-13: function で読み込む JS を最上位の `scripts` で指定する

- 最上位の `scripts` に JS ファイルを並べ、項目は関数名だけで呼ぶ。省略時は `.launcher/scripts.js`。
  ローカル設定の `scripts` は後ろに足す（ユーザー判断）
- 同じ関数名が複数のファイルにあれば、押したときにエラーにする（どちらを呼ぶか暗黙に決めないため）
- 案: 項目ごとに `file` を書く方法は、どのファイルか明確だが同じファイルを使う項目ごとに書く手間がある

### 2026-11-13: Windows でも sh を Git Bash で実行する

- Windows では Git for Windows の bash（Git Bash）で `sh` を実行できるため、sh を Windows で無効にしない。
  無効表示は `bat` だけの項目を Mac で見たときに限る（ユーザー判断）
- `bat` と `sh` を併記したら、Windows は bat、Mac は sh を実行する
- Windows の bash は Git Bash に限って探す（標準のインストール先 → PATH 上の git.exe から辿る `bin\bash.exe`）。
  PATH の `bash` は WSL の bash（`System32\bash.exe`）のことがあり、パスや環境が変わってしまうため

### 2026-11-13: ボタンの並びを改行する `break` と見出しの `heading`

- `- break` で改行、`- heading: テキスト` で改行して小さな見出しを出す（ユーザー判断）
- 案: html 項目の `<br/>` は、見た目の区切りに HTML を書くことになり YAML から意図が読みにくい。
  `rows:` で行ごとに入れ子にする案は、字下げが深くなりローカル設定での追加も複雑になる

### 2026-11-13: 実行したコマンドをプロンプトの後ろに出す

- プロンプト（作業フォルダ）の後ろに、変数を置き換えた後の本文を出す。2行目以降は `> ` で続ける。
  何を実行したか分かるようにするため（ユーザー判断）
- 出すのは10行まで。長いスクリプトで出力が埋もれないよう、それより長ければ行数だけ添える
- 案: `set -x` のように実行のたびに表示する方法は、出力そのものを変えてしまうため採らない

### 2026-11-13: 設定ファイルの変更を見張って読み直す

- 読み込みで読もうとしたファイル（work.launcher・ローカル・include 先・style・console）だけを見張る。
  案件のリポジトリには node_modules などがあり、フォルダごと見張るのは重いため
- `fs.watchFile`（0.5秒おきに更新日時を確かめる）を使う。エディタは保存時にファイルを置き換えることが多く、
  `fs.watch` ではその後の変更を取りこぼすため。数ファイルなので負荷は小さい
- 読み直しても、開いているタブと実行中のコマンドはそのままにする

### 2026-11-13: アイコンは Lucide、scripts の既定は .launcher/scripts/ の JS すべて

- アイコンセットは Lucide（約1,500個、線画で控えめ、ISC ライセンス）。`icon` に名前（`folder`・`file-text` など）を書く。
  案: Codicons（数が少なく CC BY 4.0 のクレジット表記が要る）、Material Symbols（フォントで数MBと大きい）（ユーザー判断）
- 名前で引くため全アイコンを同梱する（画面側の JS が約570KB → 約2.0MB。ローカルから読むデスクトップアプリなので許容）。知らない名前は表示せず警告を出す。
  配布物には同梱ライブラリのライセンス表記が要る（配布のフェーズで扱う）
- `scripts` にはフォルダも書け、その中の `.js` を名前順にすべて読む（サブフォルダは見ない）。
  省略時は `.launcher/scripts/`。ファイルを置くだけで使えるようにするため（ユーザー判断）

### 2026-11-13: 組み込みのヘルプページ

- アプリの使い方のヘルプを、設定に書かなくても最後のタブとして出す（ユーザー判断）。予約 ID は `help`
- 案件ごとのマニュアル（md を並べるページ）は `help` から `manual`（`.launcher/manual/*.md`）に名前を移す。後のフェーズで作る
- 書き方の例の横に、その設定で実際に出るボタンを本物の描画で並べる。例の YAML と見本がずれないよう、
  例を実際の読み込み処理に通して見本と一致するかをテストで確かめる
- アイコンは同梱しているので、ヘルプ内に検索付きの一覧を置く（オフラインでも見られる）。Lucide のサイトへのリンクも置く
- アイコン名は、まず名前どおりに引き、無ければハイフンと大文字小文字を無視して引く（Lucide の名前の付け方と
  機械的な変換が合わないものが4個あるため。無視すると同じになる組は LetterS / Letters の1組で、名前どおりで区別できる）

### 2026-11-13: 名前を WorkLauncher にする

- アプリ名は WorkLauncher（案件に限らず作業全般のランチャーのため。ほかと紛れにくいことも確かめた）（ユーザー判断）
- リポジトリ・パッケージ名は `work-launcher`、表示名は `WorkLauncher`、アプリ ID は `io.github.kazunori0909.worklauncher`
- 設定ファイルは `work.launcher`、個人用は `work.local.launcher`。拡張子 `.launcher` はそのまま
- 変数 `${projectDir}` と「案件」という言葉は残す（意味が通じ、変える影響が大きいため）
